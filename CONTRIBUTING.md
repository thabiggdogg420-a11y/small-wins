# Contributing

Start with a small change and describe the problem it solves. For a substantial feature, open an issue first so the scope and maintenance cost can be discussed. An issue is not a promise of acceptance or a delivery date.

1. Read the README and the notices covering the files you will change.
2. Make your change on a branch; keep unrelated formatting and generated outputs out.
3. Run the documented checks relevant to your change. State exactly what ran, what failed and what remains untested. Include browser/version and keyboard/mobile checks for UI work.
4. Submit a pull request describing the change, reproduction steps, verification and known limitations.

## Privacy and security

Use fictional examples. Never attach personal plans, family details, photos, learner prompts, browser profiles, database exports, credentials or private conversation history. Remove sensitive material from screenshots and logs. Do not post exploitable security details or secrets in public issues; a private reporting route must be agreed with the maintainer before sharing them. No private reporting address is currently documented here.

Do not introduce new analytics, external transmission, account access, spending or deployment automation as an incidental part of a fix. Explain any such proposal first. Tests must not submit real feedback or modify production data.

## Rights

Do not upload third-party code, assets or datasets without their applicable terms and attribution. Public availability alone does not establish permission to reuse. Preserve existing notices; do not replace them with a project-wide license. Original platform code is MIT-licensed. See THIRD-PARTY-NOTICES.md for the scope and exclusions.

## Review

Keep feedback respectful and concrete. The maintainer reviews contributions before merging; opening a pull request does not authorize deployment. Use the README's help-wanted list for useful starting points.
